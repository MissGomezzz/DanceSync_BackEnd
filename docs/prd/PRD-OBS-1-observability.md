# PRD: Observability (OBS-1)

When a battle session degrades (latency goes up, errors grow or a battle-service
replica dies), the team can see it on a dashboard within seconds, an alert fires in
under a minute, and any request or real-time event can be followed across the
gateway, battle-service and users-service with one correlation id.

## The scenario

| Part | OBS-1 |
|---|---|
| Source | Development and operations team, and the business owner |
| Stimulus | During a game session the service degrades: latency goes up, errors grow or a replica goes down |
| Artifact | API gateway, battle-service, users-service, Redis and PostgreSQL, with their logs, metrics and two dashboards (business and technical) |
| Environment | Operation with real users or during a load test |
| Response | Structured JSON logs with a correlation id generated by the gateway and propagated to the other services and to Socket.IO events; Prometheus-format metrics in every service, scraped by Prometheus and shown by Grafana in the two dashboards; an alert rule fires on degradation |
| Response measure | Metrics visible with at most **15 s** of delay; degradation detected and alerted in **under 1 min**; an event can be traced through the **three services** with its correlation id |
| Tactics | Detect faults: monitor and heartbeat. Testability: record and observe system state (logging and metrics) |

## Where we start (main, 23a903c)

The scenario's "current state" says nothing exists; part of it already does.

| Area | Already there | Missing |
|---|---|---|
| Correlation id | The gateway's `CorrelationIdFilter` keeps a valid incoming `X-Correlation-Id` or generates a UUID, echoes it and forwards it on every route, Socket.IO included. battle-service reads it on HTTP (`httpAuth.ts`) and on the handshake (`socket.data.correlationId`) | Used only in security audit lines. users-service ignores it. battle-service does not send it to users-service (`HttpMatchResultPublisher`). Normal events are never logged with it |
| Logs | JSON audit lines (`auth.rejected`, `abuse.*`) in the gateway and battle-service | Everything else is plain text: about 30 `console.*` calls in battle-service, default Logback in both Java services |
| Metrics | Actuator in the gateway and users-service; `/api/battles/health` and `/health/ready`; `RedisRoomRepository.stats` (conflict counters) | No `micrometer-registry-prometheus`, no `prometheus` endpoint, no metrics library in battle-service. Gateway `/actuator/**` (other than health) requires a signed-in user |
| Stack | `docker-compose.scale.yml` (2 battle replicas, Redis, nginx) and `docker-compose.failover.yml` (adds users-service and PostgreSQL) | No Prometheus, Grafana or exporters. No compose file runs the gateway |

## Quick path (implementation order)

1. **Structured logs and correlation id** in the three services, including the call from battle-service to users-service.
2. **Metrics endpoints**: Micrometer Prometheus registry in the Java services, `prom-client` in battle-service, plus the business and technical metrics below.
3. **Local observability stack**: one compose file with the gateway, users-service, 2 battle replicas, nginx, Redis, PostgreSQL, the Redis and PostgreSQL exporters, Prometheus and Grafana.
4. **Dashboards and alert rules** provisioned as code (versioned JSON and YAML).
5. **Measure** the three response measures with scripts, write the README section and charts like DIS-1 and REN-1.
6. **Azure**: not in this scope (see [Azure](#azure)).

## Design decisions

| Topic | Decision | Why |
|---|---|---|
| Correlation id owner | The gateway keeps generating it (existing filter). Services never generate one when the header is present; they generate one only for traffic that does not come through the gateway (direct calls, timers) | One id per request, created at the edge, as the scenario says |
| Socket.IO events | Every event log line carries the connection's `correlationId` (from the handshake) plus the event name and `roomId` | The handshake goes through the gateway, so the id is already gateway-generated |
| Battle as the traced unit | When a battle starts, battle-service stores the `correlationId` of the `battle:start` event in the battle state. Timer-driven logs (rounds, finish) and the outbox entry carry it, and the PUT to users-service sends it as `X-Correlation-Id` | The finish is driven by a timer, not by a request; this is the only flow that touches all three services, so it is the one that proves the trace |
| Log format, Java | Spring Boot structured logging (`logging.structured.format.console=ecs`) with the correlation id in the MDC: a servlet filter in users-service; an explicit access-log line per request in the gateway (reactive, so no MDC) | Built into Spring Boot 4.1, no extra dependency |
| Log format, battle-service | `pino` replaces `console.*`; one child logger per socket with `correlationId`, `socketId`, `userKind`; tokens and secrets are never logged (same rule as `authAudit.ts`) | Fast JSON logger, the de facto choice for Node |
| Audit lines | Kept as they are, same logger names and fields | Audit is the teammates' scope; the new logs live next to them, not on top |
| Metrics exposure | battle-service serves `/metrics` on a separate port (`METRICS_PORT`, default 9464). The Java services serve `/actuator/prometheus` on a separate management port. None of them is routed by the gateway or nginx | Metrics stay internal, and the gateway's security rules do not change |
| Label cardinality | No `roomId`, `userId` or `correlationId` labels on metrics. Labels are bounded: event name, outcome, user kind, HTTP route template, status | High-cardinality labels break Prometheus; ids belong in logs |
| Global vs per-replica values | Values read from Redis (active rooms) are the same on every replica: dashboards use `max()`. Per-replica values (connections, CPU) use `sum()` or show per `instance` | Avoids counting a room twice with 2 replicas |
| Scrape and refresh | Scrape and rule evaluation every 5 s, Grafana refresh 5 s | Worst case about 10 s from event to panel, under the 15 s target |
| Alerts | Prometheus alerting rules (versioned file), shown in Grafana. No notification channel (email, chat) in this scope | The scenario asks for a rule that fires and is measured; notifications add accounts and secrets for no extra evidence |
| Local stack | A new `docker-compose.observability.yml` with every service, including the gateway with the fake Entra issuer already used by the failover harness | DIS-1 and REN-1 were measured locally; Prometheus scrapes each replica by container name, so "replica down" is a real `up == 0` |

## Metrics

Names use the `dancesync_` prefix in battle-service. The Java services keep Micrometer's names (`http_server_requests_seconds`, `jvm_*`, `process_*`, `hikaricp_*`).

### Business dashboard

| Panel | Metric | Where it is counted |
|---|---|---|
| Active users (signed-in and guests) | `dancesync_socket_connections{kind="user"\|"guest"}` gauge, `sum()` | `io.on("connection")` and disconnect in `socketHandlers.ts` |
| Active rooms | `dancesync_rooms_active` gauge read from Redis, `max()` | Room sweep, every 15 s |
| Battles started | `dancesync_battles_started_total` | `announceBattleStarted` |
| Sessions started (sign-ins and guest entries) | `dancesync_sessions_started_total{kind="user"\|"guest"}` | Guest: `IssueGuestToken`. Signed-in: an authenticated handshake of a user not seen in the last 30 min (see [Assumptions](#assumptions)) |
| Spectator votes | `dancesync_votes_total` | `VOTE_CAST` handler, after the vote is applied |
| Word race rounds played | `dancesync_word_rounds_total{outcome="won"\|"expired"}` | The replica whose compare-and-set applied (`WordRaceScheduler` open/expire, word claim), so each round is counted once |
| Most used features | `dancesync_socket_events_total{event}` | Every handled Socket.IO event |
| Average battle duration | `dancesync_battle_duration_seconds` histogram | The replica that finishes the battle (`announceBattleFinished`) |

### Technical dashboard

| Panel | Metric |
|---|---|
| HTTP response time, average and p95 | `http_server_requests_seconds` (gateway, users-service, with percentile histograms on) and `dancesync_http_request_duration_seconds` (battle-service) |
| Real-time event latency, p95 | `dancesync_socket_event_duration_seconds{event}` histogram: from receiving the event to emitting the result |
| Concurrent connections per replica | `dancesync_socket_connections` per `instance` |
| CPU and memory per replica | `process_cpu_seconds_total`, `process_resident_memory_bytes`, `nodejs_eventloop_lag_seconds` (prom-client defaults); `process_cpu_usage`, `jvm_memory_used_bytes` (Micrometer) |
| Errors and exceptions | `dancesync_errors_total{source}` (battle-service), 5xx in `http_server_requests_seconds` |
| Rejected or rate-limited events (SEG-2, SEG-3) | `dancesync_auth_rejected_total{channel}`, `dancesync_abuse_events_total{action="limited"\|"blocked"\|"refused"}` next to the existing audit calls; `gateway_auth_rejected_total`, `gateway_rate_limited_total{policy}` in the gateway |
| Results waiting for users-service | `dancesync_match_outbox_pending` gauge (DIS-1 outbox) |
| Redis contention | `dancesync_room_conflicts_total{result="retry"\|"failure"}` from `RedisRoomRepository.stats` |
| Redis and PostgreSQL | `redis_exporter` (up, memory, clients, commands/s) and `postgres_exporter` (up, connections), plus `hikaricp_*` from users-service |
| Targets up | `up` per job and instance |

## Alert rules

Thresholds follow REN-1 (p95 ≤ 300 ms). Each rule has a `for:` so that one bad scrape does not fire it.

| Alert | Expression (summary) | `for` | Worst-case time to fire |
|---|---|---|---|
| `BattleReplicaDown` | `up{job="battle-service"} == 0` | 15 s | about 30 s (scrape 5 s + timeout 3 s + 15 s + evaluation 5 s) |
| `ServiceDown` | `up == 0` for gateway, users-service, Redis or PostgreSQL exporters | 15 s | about 30 s |
| `HighHttpLatency` | p95 over the last 30 s > 300 ms | 15 s | about 50 s |
| `HighRealtimeLatency` | `dancesync_socket_event_duration_seconds` p95 over 30 s > 300 ms | 15 s | about 50 s |
| `HighErrorRate` | 5xx or `dancesync_errors_total` > 5 % of requests over 30 s | 15 s | about 50 s |

## How each measure is verified

The scripts go in `load-tests/scripts/` and write JSON reports to `load-tests/reports/`, like the DIS-1 harness.

| Measure | Script | Pass |
|---|---|---|
| Metrics delay ≤ 15 s | `obs-metrics-lag.mjs`: creates rooms through the gateway at a known time and polls the Prometheus API until `dancesync_*` counters reflect them; repeated 20 times | max ≤ 15 s (plus the 5 s Grafana refresh, reported separately) |
| Alert < 1 min | `obs-alert-time.mjs`: during a load run, `docker kill` one battle replica and poll Prometheus `/api/v1/alerts` until `BattleReplicaDown` is firing; a second case adds latency (Redis slowed with `DEBUG SLEEP` or a CPU limit) until `HighRealtimeLatency` fires; 5 runs each | every run < 60 s |
| Trace through 3 services | `obs-trace.mjs`: opens the handshake and starts a battle with a known `X-Correlation-Id` through the gateway, lets it finish, then searches `docker compose logs` of the gateway, battle-service and users-service for that id | the id appears in all three, ending with the users-service line for `PUT /api/matches/{battleId}` |

The README gets an "Observability (OBS-1)" section with the results table, charts generated from the reports, and screenshots of both dashboards and a firing alert.

## Assumptions

| Topic | Assumption |
|---|---|
| Signed-in sessions | The frontend has no sign-in call to the backend (sign-in happens with Entra in the browser). A session starts at an authenticated Socket.IO handshake of a user with no handshake in the last 30 min, deduplicated across replicas with a Redis key (`SET NX` with a 30 min TTL). Reconnects and page reloads inside that window do not count. No frontend change |
| Real-time latency | Measured inside battle-service (receive to emit). The client-side p95 stays in REN-1's load tests |
| Retention | Prometheus keeps 7 days locally; Grafana uses provisioned dashboards and an anonymous viewer role on localhost only |
| Credentials | Grafana's admin password comes from an environment variable, never committed |

## Azure

Decided on 2026-11-15: **local only**, to save the student cloud credit. The code (logs, correlation id, metrics endpoints) ships to Azure with the normal deploys, but Prometheus and Grafana are not deployed there.

Deploying them later would take two more Container Apps, and a sidecar in each battle-service replica that scrapes `localhost:9464` and remote-writes to Prometheus, because Container Apps does not let a scraper reach each replica on its own (the internal address balances between replicas). In Azure, the JSON logs can already be searched by `correlationId` in Log Analytics.

## Out of scope

- **Audit trail** (who did what and when, retention, tamper protection): owned by teammates. This work does not change the audit loggers or their fields.
- Distributed tracing with spans (OpenTelemetry, Jaeger, Tempo): the scenario asks for a correlation id in the logs, not spans.
- Log aggregation (Loki, Elasticsearch): logs are searched with `docker compose logs` locally and Log Analytics in Azure.
- Alert notifications (email, chat).
- Frontend metrics (Web Vitals).

## Verification checklist

- [ ] Every log line of the three services is one JSON object with `service`, `level`, `timestamp` and, when there is one, `correlationId`.
- [ ] A request with a known `X-Correlation-Id` through the gateway appears with that id in the gateway, battle-service and users-service logs.
- [ ] No log line contains a token, the guest secret or the Redis password.
- [ ] `/metrics` and `/actuator/prometheus` are not reachable through the gateway or nginx.
- [ ] Prometheus shows every target `up`; both dashboards load from provisioned files.
- [ ] `obs-metrics-lag`, `obs-alert-time` and `obs-trace` reports meet the three measures.
- [ ] Existing tests still pass (battle-service with and without `TEST_REDIS_URL`, both Java services).
